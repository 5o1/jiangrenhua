# 证据与引用规则

## 内部证据

先定位项目明确指定的状态入口，再按需要读取源码、配置、日志和产物。聊天记录可用于寻找线索，不能覆盖仓库中更新、更具体的证据。

为关键陈述记录以下字段：

| 字段 | 含义 |
|---|---|
| claim | 准备写入论文的陈述 |
| status | 已实现、已运行、观察、推断或计划 |
| source | 文件、行号、日志、模型或数据路径 |
| scope | 适用的版本、数据集、seed 和硬件 |
| uncertainty | 尚缺哪些核验 |

数字结果必须带分母和评测单位。例如，说明是 11 个场景、11 条轨迹，还是 11 次独立成功。`best-of-N`、结束时成功率和逐 seed 成功率不能混用。诊断性小样本应标明用途，不能包装成统计结论。

## 外部证据

优先级通常为：论文正式页面或原文、官方文档、官方源代码、维护者发布说明。博客和二手综述只用于发现线索。技术问题优先使用原始资料，不用搜索结果摘要代替阅读来源。

每条外部引用都应回答两个问题：

1. 来源是否真实存在，作者、标题、年份和链接是否一致？
2. 来源是否直接支持正文附近的具体陈述？

限制直接引用长度，优先使用准确转述。来源没有声称的性能、功能或因果关系不能由作者补写。访问官方代码时，说明它证明的是默认参数、实现路径还是某个特定提交的行为。

## 引用闭合

交付前检查：

- 正文每个引用编号都有参考文献条目；
- 每个参考文献条目至少在正文出现一次；
- 编号连续且没有重复条目；
- 链接指向论文、文档或代码原页；
- 项目内部文件与公开参考文献分开说明；
- 动态网页注明访问日期；
- 提交号、数据版本和模型检查点尽量使用完整标识。
