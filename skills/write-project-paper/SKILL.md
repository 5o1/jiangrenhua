# 项目论文写作

把仓库、实验记录、代码和外部原始资料整理成可审查的中文论文。论文应帮助没有领域背景的读者理解任务、方法、证据和边界，同时保留复现所需的技术细节。

## 输出格式

遵循用户指定的格式；未指定时沿用项目已有格式，无既有约定时默认 HTML。只有用户明确要求 PDF 时才生成和检查 PDF。仅交付 HTML 时，直接检查 HTML 的内容、链接和浏览器显示；不额外导出 PDF，不安装 PDF 专用依赖，也不因缺少 PDF 阻塞交付。复审记录中将 PDF 专属项标为“不适用”。

## 先建立证据边界

1. 读取仓库入口文档、任务状态、设计记录、关键代码、配置、日志和已有结果。遵守项目自己的 `AGENTS.md` 或同类说明。
2. 建立内部证据表，区分“已经实现”“已经运行”“观察到的结果”“合理推断”“计划工作”。不要把计划、一次观察或兼容性代码写成已完成结论。
3. 记录实验对象、数据划分、模型版本、提交号、硬件、关键参数和结果分母。缺失的信息应直接标为缺失。
4. 外部研究、软件行为或版本信息需要联网核对时，使用论文原文、官方文档或官方代码。正文引用必须能够直接支持附近的陈述。

需要更细的取证和引用规则时，读取 [references/evidence-and-citations.md](references/evidence-and-citations.md)。

## 按阶段完成，不得一次生成后直接交付

写论文必须经过下面六个阶段。不得在同一次起草中把“写完、复审、验收”合并成一个模糊步骤，也不得只运行检查脚本就宣称复审完成。

1. **证据清点**：列出项目内证据、外部来源、能够支持的结论和仍然缺失的信息。
2. **结构设计**：写出章节顺序，并为每节注明它要回答的问题、依赖的证据以及读者此前必须已经知道的概念。
3. **正文初稿**：根据证据和结构写作；此阶段不宣称成品已经通过审查。
4. **四轮人工复审**：严格按“事实与引用 → 初学者阅读连续性 → 方法与复现 → 中文语言与版式”的顺序逐轮进行。每轮先记录问题，再修改正文，然后重新检查本轮受影响的项目，才能进入下一轮。
5. **展示与检查**：按用户要求的格式检查成品。HTML 检查内容、链接和浏览器显示；仅在明确要求 PDF 时渲染并检查 PDF 页面。自动检查只能补充第四轮，不能替代前四轮。
6. **交付**：只有复审记录中的必填项都有结论、发现的问题已经修改或明确列为限制，才能称为完成。

在论文源文件旁创建 `<论文文件名>_review.md`，使用 [references/review-record-template.md](references/review-record-template.md) 的结构逐项填写。每一项必须填写以下三部分：

- 结论：`通过`、`需修改` 或 `不适用`；
- 证据：具体文件、行、实验记录、引用或被检查的页面；
- 处理：做了什么修改，或为什么不适用。

不得预先把全部项目标为通过。不得用“已全面检查”“符合要求”等总括句代替逐项填写。发现问题后，应先保留发现记录，再补充修改结果；这样 review 文件能够说明论文是怎样被修正的。若关键证据缺失，正文应降低结论强度并在 review 记录中保留限制，不能猜测填补。

## 组织论文

按材料选择章节，不强行套用固定目录。通常需要形成以下阅读顺序：

- 研究问题、任务边界和当前结论；
- 相关工作的方法、它解决的问题、局限，以及本项目采用或未采用的部分；
- 初学者理解后文所需的机器人、学习和系统概念；
- 系统输入、输出、数据流、训练和执行路径；
- 项目相对上游开源软件新增或修改的内容；
- 可实际执行的 step-by-step 教程；
- 数据、实验设计、结果、失败模式和局限；
- 代码、数据、配置和版本的复现状态；
- 参考文献。

定义术语后再使用缩写。第一次出现的每个模块都说明其输入、输出、职责和不负责的事项。相关工作不能只列名词；至少解释方法机制、所解决的问题和它与当前项目的关系。

研究论文还须明确论证动作的责任者：研究设计、方法取舍、证据筛选、观察和解释由谁完成，就让谁在句中承担这些动作。对于本项目的选择与判断，适时使用“我们”“本研究”或“本文”；介绍前人工作时写明作者；描述物理结果或模块行为时，物体、数据和系统仍可作主语。不要按代词出现次数定配额，也不要把尚未完成的计划改写成“我们已完成”。具体审查方法见 [references/authorial-voice-harness.md](references/authorial-voice-harness.md)。

## 先写行为，再决定是否需要术语

面向初学者时，不要把代码变量名、配置名或工程简写直接当作正文语言。先说明读者能观察到的输入、处理和结果，再判断正式术语是否仍有用。正文必须脱离术语表也能连续读懂。

保留一个术语前，检查两个问题：后文是否会反复使用同一个精确概念；读者是否需要用这个正式名称查阅教材、论文或接口文档。两项都不满足时，直接使用普通中文。满足时，也要先说明具体含义，再在同一句或下一句给出正式名称。例如先写“根据夹爪目标位置反求六个关节角”，随后再说明“机器人学把这个计算称为逆运动学”。

项目内部表达通常应改写为实际行为：说明一个方向移动 1 cm 会让目标改变多少，不只写“增益”；说明多少毫米以内忽略、超过后怎样计算，不只写“死区”；说明新输出由当前帧和上一帧各占多少，不只写“滤波”；说明读取了什么反馈、允许相差多少、超出后怎样处理，不只写“反馈容差”；说明数据中断后保持关闭并要求人工重新启用，不只写“锁存”。命令或配置必须保留原名时，把它放在普通描述之后的括号或代码格式中。

统计词也按同一规则处理。第一次报告 p95 时写成“95% 的样本不超过……”，第一次报告 peak-to-peak 时写成“最大值与最小值之差”。不要要求初学者先理解统计缩写才能读懂实验结论。

不要用术语表修补正文中本可避免的生硬表达。只有用户明确要求速查表，或文中存在大量无法省略且已经在正文首次出现处解释过的正式概念时，才附加术语表；术语表不能替代原句改写。

教程中的命令必须来自真实入口。对每一步说明运行位置、环境、预期输出、验收条件和失败时的停止条件。涉及真机、外部发布、昂贵训练或其他高影响操作时，论文写作任务本身不构成执行授权。

## 使用图表

当架构、时序、数据流、状态迁移或多级失败条件难以用短段落说明时加入图。优先使用可复现的 HTML/SVG、表格或代码生成图；图片必须有图题，并在正文解释读者应该观察什么。图表只呈现有证据的数据，不用装饰性图像填充篇幅。

## 生成并复审成品

写完初稿后按四轮顺序复审：事实与引用、初学者阅读连续性、方法和复现充分性、中文语言与所选格式的版式。完整清单见 [references/review-checklist.md](references/review-checklist.md)。每一轮都必须先在 review 文件中逐项填写，再根据记录修改论文；修改后回到同一轮复查。不能同时填写四轮，也不能让后面一轮掩盖前面尚未处理的问题。

语言复审要逐处检查“不是……而是……”“并非……而是……”“这意味着”“值得注意的是”等模板化连接。保留确有必要的逻辑对比，重写用于制造语气或重复结论的表达。避免一句一段、无明确指代的“前文/上述/该方法”、先使用后定义的缩写，以及连续罗列抽象名词。

面向读者的正文只直接陈述实验对象、方法、证据、计算规则和适用范围，不加入“此地无银三百两”式的自证清白。删除“不是手改结果”“没有造假”“不是挑选最好案例”“没有偷偷改参数”“没有补造记录”等防御性声明。相关信息若确有方法学价值，改写成可核验的正面事实，例如“每个任务统一选取 episode0”“成功数由 50 份结果文件汇总”“实际 batch 为 64”。科学限制也优先写成适用范围或后续证据需求，例如“结论适用于这 50 类任务”“单因素贡献需要消融实验”。安全门禁、数据缺失和明确的排除条件仍应如实说明，但不得借此添加与读者判断无关的辩解。

第四轮复审必须专门搜索防御性自证措辞。发现后先判断它承载的是选择规则、证据来源、限制还是纯粹辩解，再用对应事实替换；纯粹辩解直接删除。不得仅换一个否定词保留原来的防御语气。

交付 HTML 时，使用 `scripts/audit_paper.py` 检查引用编号、模板化短语和研究者叙述视角候选段落。仅当用户要求 PDF 时，额外传入 `--pdf` 检查空白页、链接注释和 PDF 元数据。脚本的语言警告需要人工判断，不能用简单的零计数替代阅读全文。第四轮须按段落记录作者应承担的设计/解释动作与保留物体主语的理由；仍保留的候选段落用 `--voice-review` 提供逐项裁定并通过门禁，格式见叙述视角参考文件。对所选格式抽查开篇、图表、教程、结果和参考文献等实际存在的内容；HTML 不要求纸张分页检查。

最终交付应包含用户要求的成品格式、对应源文件、已填写的 review 文件、自动检查结果、未解决限制和可点击文件路径；PDF 仅在用户明确要求时包含。最终答复按四轮分别报告发现和修正，不得只给一个笼统的“review 通过”。不要擅自提交、发布或上传论文。
